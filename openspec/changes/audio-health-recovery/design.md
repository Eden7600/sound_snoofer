## Scope and evidence
The Remote API documents Command.Restart as an audio-engine restart and exposes device sample-rate readbacks and level meters. These are useful observations, not a documented end-to-end device-health guarantee. Reference: [VB-Audio Remote API, commands and physical device parameters](https://download.vb-audio.com/Download_CABLE/VoicemeeterRemoteAPI.pdf). [VB-Audio's restart guidance](https://voicemeeter.com/quick-tips-restart-the-audio-engine/) identifies engine restart as a remedy for device/audio problems.

No general stall detection is claimed yet. A feasibility task must reproduce the user's failure and establish which readings change. In particular, sample rate zero/error needs validation per supported backend/version before it can authorize automatic recovery. Some failures may leave positive sample rates, working meters and responsive API calls; those remain manual recovery cases. A constant or zero level, an unchanged parameter-dirty flag, and a silent Element return are never sufficient evidence. Normal silence, gate effects, mute and paused playback must not trigger restarts. No injected test tones, audio recording or extra device capture streams for health probes.

## Health model
Keep endpoint presence, assignment correctness, API connectivity and stream-health evidence separate. States: Unknown, No fault observed, Suspected fault, Recovery queued, Recovering, Verifying, Cooldown, Attention required. Include affected target, evidence timestamp and a concise reason. No fault observed does not mean audible audio was verified.

Poll validated cheap observations on the existing worker at a 500 ms health cadence; do not add full device enumeration to each fast settings edit. An auto-recoverable incident requires a connected, uniquely identified, managed and expected-active device with a validated fault signature for three consecutive samples spanning at least one second. Unknown/failed observations do not count as affirmative stream-fault samples. If the API is disconnected, use existing bounded connection recovery; do not repeatedly send engine commands into an unavailable API.

Suppress fault counting for five seconds after startup, resume, device assignment or engine recovery, and while an assignment transaction is pending. Reset evidence when target identity/generation changes. Normal missing endpoints use ordinary fallback and debounce rather than restarting the engine. SteamVR-ineligible devices, Source Off/unassigned strips, virtual strips without hardware streams and ASIO-patched inputs without independent devices are excluded. A1 remains relevant even when the mic is Off because it can supply the engine clock.

## Recovery policy
Auto-recover audio is a persisted toggle, initially Off. Enabling it permits only experimentally validated signatures; unsupported observations show monitoring limitations and do not silently enable heuristics.

For an eligible incident, recheck identity, signature and recorder state immediately before issuing one standalone Command.Restart = 1 through the existing single live audio owner. Do not combine it with routing writes. Do not clear/reselect devices as a speculative first step, toggle sources, release Volt A1, change sample rate/buffer configuration, reset the mixer or restart any process.

Automatic restart is deferred while recording, paused recording, tape playback or transport state is unknown. Display the reason; when transport is stopped, reevaluate the incident rather than execute a stale request. Manual restart is an explicit disruptive action: normally one activation; when transport is active or unknown, show an in-app confirmation that audio and recording may be interrupted. This is a product interaction, not a requirement to ask for implementation approval. Never automatically stop, resume, replay or start transport.

Only one recovery may be in flight. Apply a global sixty-second cooldown and at most two automatic attempts per ten minutes, persisting attempt timestamps so app relaunch cannot reset a restart storm. A backwards wall-clock change suspends automatic recovery until a trustworthy window is established. An ambiguous command outcome consumes an attempt and moves to Attention required; it is never retried automatically for that incident. Explicit user Retry may start a fresh manual attempt when no operation is in flight. A definitively accepted restart followed by a still-validated fault may get one further automatic attempt after cooldown, within budget.

## Verification and reconciliation
Pause normal native mutations while restarting, retain latest saved setting edits without blocking the UI, and reject concurrent recorder transport commands with a recovery reason. After restart, obtain fresh observations and reconcile the latest managed desired state using the existing safe planner; never restore a stale full mixer snapshot. Preserve saved mic/playback choices, native mute ownership, Volt patches, unrelated sends and unowned mixer settings. Reapply owned mute before enabling any new path; do not clear a user's mute to test sound.

Allow up to ten seconds for responsive API observations and the validated fault signature to clear. Two fresh valid health samples plus verified required managed state establish operational recovery, not proof of audibility. If that evidence is unavailable, report Recovery unverified or Attention required, not success based on the setter returning. Observe recorder state anew without changing it. Element may need separate attention after an engine restart; process presence alone does not establish host ASIO readiness.

Go cancellation cannot interrupt an arbitrary blocked DLL call. A watchdog may mark the actor stalled while leaving UI responsive, but must never issue concurrent DLL calls, abandon ownership or spawn a second writer. Forced termination/relaunch and moving native access into a helper process are outside this change; specify another OpenSpec change if the reproduced failure requires that architecture. This version reports a stuck native call as manual attention.

The Stream Deck supported action registry can optionally bind it; no default key assignment needs changing. Shared actions carry client identity and reject duplicate/in-flight requests. A small bounded diagnostic incident record may retain timestamps, evidence and outcome for troubleshooting, never audio content.

## Opt-in callback feasibility probe
The user authorized a separate callback probe on 2026-10-05. This extends the earlier passive-only investigation, not production recovery. Use a standalone Windows x64 C executable, built with the installed MSVC toolchain into `.local/stall-probe`. Register only the output-insert slot; refuse an occupied slot without unregistering another client. Copy every input channel bit-for-bit to its corresponding output; callback work is bounded memory copying and interlocked counters only, without allocation, logging, locks or Go runtime entry. Count lifecycle events, buffer callbacks and synchronized callbacks separately: callback activity alone is not a documented health guarantee. Log observations outside the callback for ten seconds, then stop/unregister/logout in order. No restart, routing setter, audio storage or automatic recovery. A process-local watchdog bounds hung native calls. A built-in self-test checks x64 ABI, pass-through including aliasing, malformed-buffer handling and event counters before any DLL is loaded. Compare stalled and healthy runs before interpreting the result.

## Production callback integration (authorized 2026-10-05)
The confirmed Volt/Potato tests authorize integrating the native output-insert callback monitor with the existing Auto-recover Audio preference (default Off). This supersedes the unavailable-capability gate above for the tested Universal Audio Volt A1 on Potato only. Other configurations remain observation/manual-recovery only. Use the existing probe's bit-preserving C callback in a shared header and a small first-party DLL shipped beside the Go executable. Load by absolute executable-relative path; do not redistribute the Remote DLL, enter Go from the audio callback, create a second login/writer, or spawn a permanent probe process. Build the native DLL with installed MSVC/SDK in the checked build script; a missing companion DLL disables monitoring with a visible reason.

Only the live worker holding audio ownership can register the monitor, and only while auto-recovery is enabled. Preview never registers a callback. Stop and unregister before releasing ownership or closing the native adapter; ambiguous cleanup retains loaded code and ownership rather than risking a stale callback. Occupied callback slots are not displaced; registration failures remain visible until the user toggles monitoring again. The callback only copies buffers unchanged and updates interlocked counters. No recording or analysis of samples.

Sample callback progress on the existing worker at no more than 500ms intervals between steps. Qualify no buffer delivery for at least two seconds and three fault observations spanning at least one second, after five seconds of grace on enable, reconnection, assignment/config identity changes, stream lifecycle changes and worker gaps over two seconds (including resume). Use the same unique physical WDM presence and ASIO matching as routing. Missing hardware blocks restart and discards qualification; reconnection starts fresh grace. No sample-rate or amplitude-based automatic trigger. Callback failures, disconnected API, unrecognized setup, ambiguous devices and unresolved/changing routing never qualify. Refresh full inventory, callback evidence and recorder transport immediately before dispatch; do not act on a cached disappearance or transport state.

Reuse the persistent sixty-second cooldown and two-attempt/ten-minute budget. Ambiguous restart outcomes block subsequent automatic attempts until explicit manual retry or demonstrable callback recovery; persist that block across app restart. Pause routing mutations while a restart is pending. Verify two advancing synchronized callback observations after restart, not merely a positive sample rate; then resume existing reconciliation using current desired state. Report processing resumed with audibility unverified. Timeout remains an unverified outcome. Unknown/active recorder transport defers automatic recovery. Continue to leave broad silence/mute, Element, recording and long-duration hardware acceptance unchecked; implementation tests cover the decision boundaries without claiming hardware coverage.

## Generalized A1 stall detection (2026-10-06)
A second incident reproduced the stall with `Speakers (3- SteelSeries Arena 9)` (WDM) on A1 while the Volt was absent. The standalone callback probe recorded 0 buffers in 10 seconds during the stall. After the user's manual engine restart, it recorded 939 synchronized buffers in 10 seconds (about 94/s, 48 kHz, 512 frames). Remote API reads succeeded throughout. See incident-2026-10-06.md. Callback delivery is therefore the stall signature for the A1 clock device generally, not only for the Volt. This section supersedes the Volt-only target and the Auto-recover coupling above.

- **Monitoring independent of recovery.** The live audio owner registers the pass-through callback monitor whenever Snoofer is live, regardless of Auto-recover. Preview still never registers, and ownership and cleanup rules are unchanged. Auto-recover only gates automatic dispatch.
- **Target:** the device currently assigned to A1, on any edition with the callback API.
  - **ASIO on A1** (the A1 name matches an enumerated ASIO driver or a configured ASIO matcher): presence keeps requiring the configured WDM presence evidence via `routing.SelectASIO`. An installed ASIO driver alone never counts.
  - **Any other A1 device:** at least one available non-ASIO output endpoint with exactly the assigned name.
  - The identity key covers assignments and the matching endpoints, so hotplug or reassignment restarts grace. No A1 assignment, absent hardware or uncertain presence never qualifies. Qualification timing (grace, 2 s without buffers, 3 samples over ≥ 1 s) is unchanged.
- **Reporting.** A qualified fault sets an explicit `Stalled` worker state, independent of presentation text:
  - **health text:** "Audio engine stalled: no callback buffers";
  - **header badge:** critical tone;
  - **audio callback monitor card:** Attention, with the stall as its error;
  - **without Auto-recover:** health adds "restart required";
  - **with Auto-recover:** the existing bounded automatic restart (cooldown, budget, recorder deferral, pre-dispatch recheck) runs unchanged.
- **GUI access.** Restart audio engine (and Confirm when required) appears on the Audio screen's Routing & recovery card and on Diagnostics, alongside Automatic recovery. Stream Deck and tray access remain.
- **Personal configuration:** Auto-recover enabled at the user's request (2026-10-06), through the GUI toggle.
