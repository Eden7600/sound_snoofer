# Volt disconnect incident — 2026-10-05

## Confirmed conditions
The user deliberately disconnected Volt with Sound Snoofer off and confirmed audio remained stalled and Volt disconnected. No restart, setter, routing change, callback or audio capture was used by the probe.

## Read-only evidence
Raw captures remain inside the repository at `.local/rollback/modular-20261005-110252/probe-evidence/stalled.log` (14:42:18–14:42:24 UTC) and `.local/rollback/modular-20261005-110252/probe-evidence/stalled-levels.log` (14:46:08–14:46:16 UTC). The opt-in `TestStalledEngineProbe` uses one locked OS thread and logs native calls before and after execution.

- Login, parameter refresh and reads succeeded throughout both captures; edition was Potato.
- Twelve samples per capture reported A1, A2, Strip 1 and Option sample rates of 48,000 Hz.
- A1 retained `Universal Audio Volt`; A2 retained `Speakers (3- SteelSeries Arena 9)`.
- Physical Volt WDM endpoints were absent from input/output inventory. The installed Volt ASIO driver still enumerated; this is not hardware-presence evidence.
- Recorder raw flags were record=0, stop=1, pause=0, play=0.
- The second capture sampled all 34 Potato input channels at pre-fader, post-fader and post-mute, plus all 64 output channels, twelve times: 1,992 meter reads, all value=0 and return code=0.
- An earlier CLI inventory probe timed out without output. Its cause is unresolved; the successful direct capture does not support claiming that the Remote API was hung.

## Conclusions and limits
The current nonpositive-A1-sample-rate check misses this confirmed failure. Positive sample rates, successful API calls and unchanged parameter-dirty flags do not establish running audio. Zero meter values do not distinguish the failure from silence, mute or inactive sources. The documented passive getters examined expose no explicit engine-running heartbeat.

An assigned A1 Volt with absent physical Volt endpoints is actionable device-disconnect evidence, not a validated general stall signature. It can support an honest disconnected-clock-device warning. It does not yet justify automatic engine restart: compare reconnect-only behavior, then a controlled restart if audio remains stalled. In particular, restarting while the clock hardware remains absent may not restore audio.

Automatic recovery remains gated off. No production behavior changed. Recovery verification must continue to say audio continuity is unverified when only API/sample-rate observations pass. Reconnection, restart effectiveness, audible output, Element and recorder effects are not validated by these captures.

## Reconnected, still stalled
The user reconnected Volt without restarting and confirmed audio remained stalled. Capture `.local/rollback/modular-20261005-110252/probe-evidence/reconnected-stalled.log` began at 14:47:36 UTC. Volt WDM input `INPUT 1/2 (Volt 2)` and output `MONITOR L/R (Volt 2)` returned, while A1/A2 still reported 48,000 Hz, all native reads succeeded, and all 1,992 meter readings remained zero. Presence restoration therefore does not establish audio recovery either.

This supports investigating a bounded, event-based recovery after a witnessed A1 device disconnect/reconnect, rather than asserting a general live stall detector. It needs a controlled restart comparison and repeated healthy hotplug tests before automatic dispatch. Sound Snoofer launched only after reconnection cannot infer this incident from current presence and sample-rate values alone; retaining a witnessed incident across reconnection would be necessary. Current specs still require ordinary fallback for missing devices; any automatic post-hotplug restart policy needs an explicit design update and validation.

## User-confirmed callback stall and recovery sequence
The user supplied three captures and explicitly confirmed the actions on 2026-10-05:

| `.local/rollback/modular-20261005-110252/probe-evidence/callback-20261005-085943-435.log` | Started normally, then switched Volt power off during the run. | Buffer count advanced to 599 by 6.516 seconds, then remained 599 through 10.016 seconds. |

| `.local/rollback/modular-20261005-110252/probe-evidence/callback-20261005-090014-060.log` | Reconnected Volt, then manually restarted the audio engine during the run. | No buffers through 8.016 seconds; six by 8.516 seconds, then approximately 94 per second, reaching 147 by 10.016 seconds. |

The user described restarting halfway through the third run; the exact restart timestamp was not instrumented. Do not infer a precise recovery latency from that description. All three captures reported successful registration/start/stop/unregister/logout, no invalid/unknown callbacks and no change notifications. Ending was observed only during probe cleanup. Zero sample-rate/frame/channel fields before the first buffer are uninitialized probe observations, not native zero-sample-rate readbacks.

This establishes a candidate callback-delivery fault signature for this reproduced Volt failure: callbacks stop during the stall and resume following reconnection plus manual engine restart. Registering the probe while stalled did not itself recover audio. Earlier passive reads remained responsive and reported positive rates, so callback delivery adds evidence those reads lacked. This supersedes the outstanding stalled-callback comparison noted above, but does not establish coverage for other failures or prove audible output from callback activity alone.

Proposed integration: distinguish device absence from a connected device with sustained missing callbacks; wait for hardware to return, allow transition grace, and use successful callback registration/start plus a bounded no-buffer interval as candidate evidence. Retain existing recorder guards, one-shot restart, cooldown and restart budget. Callback return after restart is processing-progress evidence, not an end-to-end audibility guarantee. No automatic policy or production code changed in this investigation. Healthy silence/mute, normal transitions, callback-slot conflicts, prolonged operation, Element and recorder effects still require validation before enabling automatic recovery.
