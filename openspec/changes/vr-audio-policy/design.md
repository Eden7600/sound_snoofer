## Decisions
SteamVR availability is observed independently from endpoint presence. Initial runtime detection uses exact vrserver.exe process presence in the current user session; stopped and unknown both exclude VR-classified endpoints. This is runtime presence, not proof the headset is worn or its audio is healthy. Do not launch SteamVR to query availability.

Headset profiles have a stable ID, display label, separate capture/render regex matchers, and ordered profile priority. Match actual connected Windows endpoints, then associate with Voicemeeter enumeration. Profiles may describe only one direction and may associate separate headset accessories. Do not infer identity from Windows defaults, since these deliberately point at Voicemeeter. Classification precedes ordinary device matching so a headset cannot leak through broad normal-device rules while SteamVR is stopped. Unknown headset models require a user profile; do not claim universal automatic detection. Ship only validated device-name examples, not guessed Index/Beyond names.

Eligibility requires known running SteamVR AND an active, uniquely resolved endpoint for that direction. Ambiguous profiles/endpoints expose a reason and do not choose arbitrarily. Profile priority resolves distinct configured headset choices; equal ambiguous matches do not. With preference disabled, eligible VR endpoints follow configured normal priority/manual selection. With preference enabled, the highest eligible headset overrides that direction's normal selection, including a saved manual playback choice, without rewriting it. Source Off always wins. Mic and playback resolve independently. Runtime exit/disconnect restores the saved normal selection or existing fallback policy.

Avoid needless source changes: compare resolved endpoint identity, not display text; keep a valid current endpoint on equal priority. Only a policy or eligibility change that requires a different endpoint triggers assignment. Retain the existing one-second device debounce and revalidate before writes. Mute, gain and status changes never trigger reassignment. A VR mic uses a configurable unreserved hardware strip (default Potato input 4), validated against desk/lav/webcam/return reservations and edition limits. Preserve Volt channel patches and A1.

## Windows defaults
A single persisted toggle, Keep Windows defaults on Voicemeeter, defaults Off for existing and new profiles. When enabled in live mode it applies both inside and outside VR, including after SteamVR exits. Target render endpoint is the configured primary Voicemeeter virtual input; target capture endpoint is the configured application microphone output (B3 in the Potato profile). Resolve endpoint direction and ID explicitly; never confuse Voicemeeter Input with the Windows capture endpoint. Cover Console, Multimedia and Communications roles in each direction. Validate configured targets uniquely and as active before any write in that direction.

An independent bounded Windows worker owns COM initialization, endpoint notifications, role readback and default-setting calls. For the first implementation, poll default-role IDs every 100 ms on this independent worker instead of registering COM notification callbacks. This avoids callback lifetime and apartment reentrancy hazards; the bounded polling cost is twelve small read calls per cycle, not full device enumeration. Resolve targets on configuration change or a five-second inventory refresh, and verify after writes. Suppress self-notification loops. Limit correction to three attempts per direction in ten seconds; persistent contention becomes a visible error until explicit Retry or toggle off/on. No unbounded battle with SteamVR. Endpoint reappearance may reconcile unavailable targets; it does not clear a contention suspension.

Default-setting implementation is a feasibility gate: isolate any undocumented Windows policy interface behind a small adapter and validate supported Windows versions before shipping. The public notification API is not a default setter. Unsupported platforms must report unavailable and leave defaults alone; do not silently modify registry or SteamVR settings. Disabling protection or exiting Snoofer stops enforcement and leaves current defaults unchanged. Do not restore a stale snapshot or change per-application device assignments. Dry-run observes and previews only.

## UI and migration
Controls adds two independent headset preferences and default protection, with runtime/endpoint availability explanation. Saved preferences remain visible while unavailable. Yellow means pending verification; red plus text explains an unmet preference or failed protection. Graph remains observed routing, not an assumed working headset path. Existing profiles migrate with preferences and protection Off; no new automatic source changes until configured. Missing SteamVR is normal, not a startup error.

## Sources and feasibility
- Valve exposes headset audio endpoint properties in [OpenVR headers](https://github.com/ValveSoftware/openvr/blob/master/headers/openvr.h). Using them for discovery is a possible later enhancement; this version relies on configurable regex profiles and does not add an OpenVR runtime dependency.
- [Windows endpoint notifications](https://learn.microsoft.com/en-us/windows/win32/api/mmdeviceapi/nn-mmdeviceapi-immnotificationclient) provide default-change observation.
- [Windows device roles](https://learn.microsoft.com/en-us/windows/win32/coreaudio/device-roles) separate the three roles and capture/render directions.

Hardware acceptance must establish actual Index/Beyond endpoint names, Windows policy compatibility, and behavior when SteamVR repeatedly changes defaults. A brief startup diversion may precede notification correction; do not promise sample-accurate continuity.
